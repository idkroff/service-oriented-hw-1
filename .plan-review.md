# Валидация плана HW7

## Пререквизит (extract auth)

**Вердикт:** 8/10 — реализуемо, но содержит несколько серьёзных технических ловушек

**Риски:**

1. **arm64 / GitHub Actions несовместимость (КРИТИЧНО).** Все Dockerfile и `docker-compose.yml` содержат `platform: linux/arm64`. GitHub Actions runners работают на `linux/amd64`. Без изменений ни `docker compose up`, ни `docker build` в CI **не пройдут**. Нужно либо убрать `platform:` директивы (и тогда работает на обоих), либо добавить `--platform linux/amd64` в CI и multiarch-build через `docker/setup-qemu-action`. Текущий план это полностью игнорирует.

2. **Одна Postgres — конфликт миграций.** `marketplace-api` запускает `goose -dir /app/migrations postgres "$DATABASE_URL" up` при старте (см. `entrypoint.sh`). Если `user-service` будет делать то же самое с тем же `DATABASE_URL` (одна БД), два контейнера при параллельном старте могут вызвать race condition на `goose_db_version` таблице. Goose использует advisory lock, но только при `goose.SetDialect("postgres")` — `goose` CLI берёт его автоматически, однако если обе миграции создают `user_role` enum (он уже есть в `00001_init.sql` marketplace-api), вторая миграция упадёт с `type "user_role" already exists`.

3. **DROP FK + существующие данные.** Миграция `00003_drop_user_tables.sql` должна сначала дропнуть FK constraints `products.seller_id → users(id)` и `orders.user_id → users(id)`, а затем таблицы `users`, `refresh_tokens`. Но `order_items.product_id → products(id)` тоже зависит от `products`, а `user_operations.user_id → users(id)` не упомянута в плане и тоже упадёт. Нужно добавить `ALTER TABLE user_operations DROP CONSTRAINT ...` или `DROP TABLE user_operations` (и пересоздать без FK к users).

4. **`/auth/validate` не описан в OpenAPI user-service.** План говорит «через OpenAPI его можно не описывать». Это рискованно, т.к. без спеки теряется контрактное тестирование и самодокументация. Лучше завести хотя бы минимальную спеку.

5. **Middleware.Auth → HTTP-клиент.** Текущий `middleware.Auth` синхронно вызывает `verifier.VerifyAccessToken(token)` — это in-process. После рефакторинга каждый авторизованный запрос получит сетевой вызов к user-service (+~5-10ms). Это повлияет на p95 latency в нагрузочных тестах (пункт 7/8). План учитывает «таймаут 2s + retry», но не описывает circuit breaker / caching JWT.

6. **`user-service` Dockerfile.** Текущий Dockerfile user-service делает `go mod init user-service && go build -o user-service .` — нет `go.mod` на диске. После рефакторинга Dockerfile нужно переписать полностью (goose, миграции, entrypoint.sh). План это упоминает, но Dockerfile user-service не копирует entrypoint.sh.

**Рекомендации:**

- Убрать `platform: linux/arm64` из **всех** Dockerfile (`FROM --platform=$BUILDPLATFORM ...` или просто `FROM golang:1.23-alpine`) и из `docker-compose.yml`. Добавить в CI `DOCKER_DEFAULT_PLATFORM=linux/amd64` если нужно.
- Использовать **отдельные базы данных** (или хотя бы отдельные схемы) в одном Postgres: `POSTGRES_DB: marketplace` для marketplace-api, создать `user_db` через init-script (`/docker-entrypoint-initdb.d/`). Это изолирует миграции.
- Если оставить одну БД — user-service миграции НЕ должны создавать `user_role` enum (он уже есть от marketplace-api migration). Использовать `CREATE TYPE IF NOT EXISTS` (Postgres 9.1+ не поддерживает, нужен DO-блок).
- Добавить `depends_on: user-service: condition: service_healthy` в marketplace-api (уже в плане), но user-service ТОЖЕ зависит от `postgres: condition: service_healthy` — в текущем compose `user-service` не имеет `depends_on: postgres`.

## Пункт 1 — CI pipeline

**Вердикт:** 7/10 — структура адекватна, но блокируется проблемой arm64

**Риски:**

1. **arm64 блокирует весь CI.** `docker build` с `FROM --platform=linux/arm64` на `ubuntu-latest` (amd64) вызовет qemu emulation (если установлен setup-qemu) или hard fail. Без QEMU — ошибка формата `exec format error`. С QEMU — сборка Go в эмуляции ~5-10x медленнее.

2. **Matrix `service: [marketplace-api, user-service]` для lint-build.** Хорошая идея, но `user-service` пока не имеет `go.mod` на диске — в плане указано «завести go.mod», но если забыть — CI сломается.

3. **Integration-tests через GH Actions services-блок.** Сервис Postgres в `services:` запускается на хосте, но оба Go-сервиса запускаются как Docker-контейнеры. Контейнерам нужен `--network host` или docker network для связи с Postgres service. Проще: использовать `docker compose up` целиком (как в e2e). Смешение подходов (GH services + docker run) — источник ошибок.

4. **`needs: lint-build → unit-tests → integration-tests → e2e-tests`.** Последовательная цепочка означает, что весь CI занимает sum(jobs). Для домашки это ОК, но время будет ~15-20 минут из-за docker builds.

5. **Артефакты.** План упоминает `docker compose logs` как артефакт. Нужно добавить `actions/upload-artifact@v4` с path и `if: always()`, иначе логи пропадут при падении.

**Рекомендации:**

- Удалить `--platform=linux/arm64` из всех Dockerfile; в compose не указывать `platform:`.
- Использовать Docker layer caching (`docker/build-push-action` с `cache-from: type=gha`) для ускорения.
- В `lint-build` добавить `golangci-lint` (не только `go vet`), чтобы lint был реальным.
- `integration-tests` и `e2e-tests` лучше объединить: оба поднимают docker compose, разница только в уровне тестов. Или как минимум шарить docker compose up между ними через services/healthcheck.

## Пункт 2 — Integration tests

**Вердикт:** 8/10 — сценарий корректный, но testcontainers vs docker-compose — неоднозначный выбор

**Риски:**

1. **Testcontainers-go + Docker-in-Docker в CI.** В GitHub Actions `testcontainers-go` работает, но требует Docker socket. С matrix + services-блоком GH это может конфликтовать. Если в `integration-tests` job используется `docker compose`, а testcontainers тоже поднимает контейнеры — возможны port collisions.

2. **`testcontainers.NewDockerCompose`** (Compose module) — это experimental API в testcontainers-go. В свежих версиях переименован в `tc.NewDockerComposeWith(...)`. Нужно убедиться в совместимости версии.

3. **Сценарий: `POST user-service/auth/register → POST marketplace-api/products`.** Правильно доказывает межсервисное взаимодействие. НО: после extract-auth, register возвращает JWT подписанный user-service. Marketplace-api отправляет этот JWT на `/auth/validate` к user-service. Значит JWT_SECRET должен быть одинаковый или user-service сам проверяет свои JWT. План подразумевает, что user-service и выдаёт, и проверяет — ОК.

4. **Прямой SQL `SELECT * FROM products`** — тест обращается к той же Postgres. Нужно знать DSN. Если testcontainers поднимает postgres — DSN доступен через `container.ConnectionString()`. Если docker compose — нужен mapped port.

5. **Идемпотентность: «каждый тест в своём пакете поднимает свежие контейнеры».** Это очень медленно (каждый тест — 10-20 секунд на старт контейнеров). Лучше: один TestMain поднимает compose, каждый тест в `t.Cleanup` чистит данные через TRUNCATE.

**Рекомендации:**

- Определиться: **или testcontainers, или docker compose up в CI**. Не смешивать. Для домашки docker compose проще и надёжнее.
- Если testcontainers — использовать `testcontainers-go v0.34+` с `compose.NewDockerCompose(...)`.
- Добавить `-tags=integration` и `//go:build integration` для разделения unit/integration при `go test ./...`.
- Тег `-count=1` правильный (отключает кеширование).

## Пункт 3 — E2E

**Вердикт:** 9/10 — сценарий полный, покрывает требования задания

**Риски:**

1. **`docker compose up -d --wait`** — работает только если все сервисы имеют `healthcheck` И compose версия >= 2.22. В текущем compose у `user-service` нет `depends_on: postgres`. После рефакторинга user-service должен зависеть от postgres healthy, иначе `--wait` может зависнуть (user-service стартует, но не может подключиться к БД → healthcheck fail → timeout).

2. **`HasActiveOrder` + rate limit в сценарии.** E2E: USER создаёт order. Если тест запускается повторно без очистки БД — `HasActiveOrder` вернёт true (предыдущий order в статусе CREATED) → тест упадёт с `ErrActiveOrderExists`. Нужен cleanup или cancel предыдущего order.

3. **`ORDER_RATE_LIMIT_MINUTES=1`** в compose. Если e2e тест пытается создать два заказа за минуту (например, для разных товаров) — второй вернёт 429. В текущем сценарии один заказ — ОК, но при расширении тестов это ловушка.

4. **SQL-проверка `products.stock = 7`.** Тест подключается к Postgres напрямую. Нужен DSN. В CI при `docker compose up` порт 5432 замаплен на host. DSN: `postgres://postgres:postgres@localhost:5432/marketplace?sslmode=disable`. Нужно передать его в тест (env var или флаг).

5. **Расположение `test/e2e/scenario_test.go`.** В плане указано в корне проекта, а не в `services/marketplace-api/test/e2e/`. Это лучше — e2e вне конкретного сервиса. Но нужен отдельный `go.mod` или тестовый пакет на уровне корня.

**Рекомендации:**

- Добавить `depends_on: postgres: condition: service_healthy` в user-service в docker-compose.yml.
- Установить `ORDER_RATE_LIMIT_MINUTES=0` в e2e compose override (или использовать отдельный `docker-compose.test.yml`).
- Добавить cleanup: TRUNCATE tables или создание уникальных пользователей в каждом прогоне.
- Для SQL-проверок использовать `pgx` напрямую в Go-тесте с `DATABASE_URL` из env.

## Пункт 4 — Prometheus + metrics

**Вердикт:** 8/10 — покрывает требования, но есть нюансы chi + oapi-codegen

**Риски:**

1. **chi.RouteContext(r.Context()).RoutePattern() — пустая строка.** Когда запрос проходит через `oapi-codegen` middleware (`nethttpmiddleware.OapiRequestValidator`), chi route pattern может быть не заполнен на момент вызова metrics middleware, если metrics middleware стоит ДО группы с роутами. Middleware порядок в текущем коде:
   ```
   r.Use(middleware.Logging)  // глобально
   r.Group(func(r chi.Router) {
     r.Use(validationMiddleware)  // внутри группы
     ...routes...
   })
   ```
   Если `metrics.go` добавить через `r.Use(metricsMiddleware)` на уровне корневого роутера — `RoutePattern()` будет пустым, т.к. chi заполняет его только после match'а маршрута. **Решение:** metrics middleware должен быть `WrapHandler` или использовать `chi.RouteContext` в defer/response wrapper, чтобы pattern уже был заполнен после обработки.

2. **`/metrics` endpoint и OpenAPI validator.** Если `/metrics` зарегистрировать внутри группы с `validationMiddleware` — валидатор вернёт 4xx (path не в спеке). План правильно говорит «регистрируется до OpenAPI-валидатора» — но нужно убедиться, что это ДО `r.Group`. Пример:
   ```go
   r.Handle("/metrics", promhttp.Handler())  // ← до группы
   r.Get("/health", healthHandler)           // ← до группы
   r.Group(func(r chi.Router) { ... })
   ```

3. **`http_request_errors_total` — что считать ошибкой?** Задание требует label `error_type`. План не определяет, что является «ошибкой»: 4xx? 5xx? Только 5xx? Рекомендация задания: status >= 500 для error counter ИЛИ любой не-2xx. Нужно явно определить. Если считать все 4xx — error rate при невалидных запросах в k6 будет искусственно высоким.

4. **Buckets для histogram.** Указаны `.005,.01,.025,.05,.1,.25,.5,1,2.5,5` — это дефолт Prometheus. ОК для HTTP-сервиса. Но если auth-validate добавляет 5-10ms к каждому запросу — нижние buckets наполнятся, а p95 может оказаться ~50ms. Это нормально.

5. **prometheus.yml: `scrape_interval: 5s`.** Для dev — нормально. Но для пункта 8 (check-sli.sh) после k6 нужно подождать хотя бы 2 scrape intervals (10s) перед query. План указывает «15s после конца» — ОК.

**Рекомендации:**

- Metrics middleware: использовать паттерн `WrapResponseWriter` + defer, чтобы `RoutePattern()` был уже заполнен:
  ```go
  func MetricsMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
      start := time.Now()
      ww := middleware.NewWrapResponseWriter(w, r.ProtoMajor)
      next.ServeHTTP(ww, r)
      // после ServeHTTP — route pattern заполнен
      pattern := chi.RouteContext(r.Context()).RoutePattern()
      ...
    })
  }
  ```
- Для `error_type` label использовать: `"client_error"` (4xx), `"server_error"` (5xx), или конкретные error codes из `mapDomainError`.
- `/metrics` регистрировать на корневом роутере вне группы с validation middleware.
- В `prometheus.yml` добавить `scrape_timeout: 5s` и label `job` для каждого target.

## Пункт 5 — Grafana service dashboards

**Вердикт:** 9/10 — план покрывает все требования, мелкие PromQL неточности

**Риски:**

1. **PromQL latency:** `histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket{job="marketplace-api"}[1m])) by (le, endpoint))` — корректно. Но label `endpoint` может быть пустым (см. пункт 4 про RoutePattern). Если пустой — все запросы агрегируются в одну серию.

2. **Error rate PromQL:** `sum(rate(http_request_errors_total{job="marketplace-api"}[5m])) / sum(rate(http_requests_total{job="marketplace-api"}[5m]))` — если `http_requests_total` = 0 (нет трафика) — деление на 0 → NaN. Нужно обернуть: `... OR on() vector(0)` или использовать `clamp_min(sum(rate(...)), 1e-10)` в знаменателе.

3. **Provisioning structure:** `infra/grafana/provisioning/datasources/datasources.yml` и `provisioning/dashboards/dashboards.yml` — правильные пути. Docker volume mount: `-v ./infra/grafana/provisioning:/etc/grafana/provisioning`. Нужно убедиться, что Grafana image не переопределяет `GF_PATHS_PROVISIONING`.

4. **JSON dashboards.** Если генерировать вручную — JSON может быть невалидным. Лучше собрать в Grafana UI и экспортировать. Plan упоминает оба варианта — ОК.

**Рекомендации:**

- Добавить `or vector(0)` в error rate panels для защиты от NaN.
- В `datasources.yml` указать `isDefault: true` и `access: proxy` (не `direct`).
- Dashboards должны содержать `__inputs` или hardcoded datasource UID. При provisioning проще всего hardcoded `uid: "prometheus"` и тот же uid в datasource yaml.
- Минимум 4 панели: latency line chart, error rate stat, RPS bar gauge, status code distribution — ОК по требованиям.

## Пункт 6 — Grafana infra dashboard

**Вердикт:** 9/10 — полностью покрывает требования

**Риски:**

2. **postgres-exporter в docker-compose.** Нужен `DATA_SOURCE_NAME` или `DATA_SOURCE_URI` env var: `postgres://postgres:postgres@postgres:5432/marketplace?sslmode=disable`. Порт экспортера: 9187.

3. **3+ панели** — план указывает 3 обязательные + optional. Минимум выполнен.

**Рекомендации:**

- Использовать образ `prometheuscommunity/postgres-exporter:v0.16.0`.
- Добавить в `prometheus.yml`: `- job_name: postgres \n static_configs: [{targets: ['postgres-exporter:9187']}]`.
- Для cache hit ratio использовать PromQL: `pg_stat_database_blks_hit{datname="marketplace"} / (pg_stat_database_blks_hit{datname="marketplace"} + pg_stat_database_blks_read{datname="marketplace"})`.
- Добавить панель deadlocks: `rate(pg_stat_database_deadlocks{datname="marketplace"}[5m])` — отвечает на «где узкое место».

## Пункт 7 — Load tests

**Вердикт:** 7/10 — серьёзный риск с POST /orders из-за rate-limit и HasActiveOrder

**Риски:**

1. **КРИТИЧНО: POST /orders в k6 при ORDER_RATE_LIMIT_MINUTES=1.** Текущая логика `usecases/order.go`:
   - `RateLimitCheck` — проверяет `user_operations` за последние N минут. Если есть запись — возвращает `domain.ErrOrderLimitExceeded` (HTTP 429).
   - `HasActiveOrder` — если у пользователя есть order в статусе CREATED/PAYMENT_PENDING — возвращает `domain.ErrActiveOrderExists` (HTTP 409).

   При 10 VUs × 60s, с 10% POST /orders = ~6 запросов/сек × 10 VUs = ~360 попыток создать заказ. С одним токеном из setup — **все после первого вернут 429 или 409**. Error rate ~99% для POST /orders. Это **сломает threshold `http_req_failed: ['rate<0.01']`**.

2. **Решения для k6:**
   - Вариант A: Создать N пользователей в setup (по одному на VU), каждый VU использует свой токен. Но HasActiveOrder всё равно блокирует — нужно cancel'ить order перед следующим.
   - Вариант B: Выставить `ORDER_RATE_LIMIT_MINUTES=0` в тестовом compose (отключить rate limit). Но HasActiveOrder всё равно будет мешать.
   - Вариант C: Каждый POST /orders → сразу POST /orders/{id}/cancel (чтобы освободить HasActiveOrder). Но rate limit на UPDATE также с тем же таймаутом.
   - Вариант D: Убрать POST /orders из k6 mix, оставить только GET /products. Тогда нагрузка нереалистична.
   - **Лучшее решение:** в k6 setup создать по пользователю на VU, в iteration: GET products (70%), GET product/{id} (20%), POST order + cancel order (10%, с уникальным товаром). Но rate limit = 1 min → в 60s тесте каждый VU сможет создать max 1 заказ. Итого: 10 заказов за весь тест. Error rate будет зависеть от логики retry/error handling в k6.

3. **`--network host` для k6 контейнер.** На Linux работает. На macOS (и в CI Ubuntu) `--network host` в Docker Desktop может не разрешать доступ к compose containers. Лучше: `docker compose run k6` или `--network=<compose_network_name>`.

4. **Thresholds.** `http_req_duration: ['p(95)<500']` — в миллисекундах (k6 default). Если auth-validate добавляет сетевой round-trip — p95 может быть ~50-100ms для простых GET. Для POST /orders с транзакциями + network call — ~100-300ms. Threshold 500ms — с запасом, ОК.

5. **Healthcheck под нагрузкой.** План: `curl /health` параллельно. Но `/health` — простой JSON-ответ, не зависит от DB. Всегда пройдёт, если сервис жив. Это не доказывает работоспособность. Лучше: healthcheck, который проверяет DB connection (текущий healthcheck этого не делает).

**Рекомендации:**

- **Обязательно:** добавить `docker-compose.test.yml` override с `ORDER_RATE_LIMIT_MINUTES=0` (или очень маленьким значением) для load-тестов.
- В k6 сценарии: создать ОТДЕЛЬНОГО пользователя на каждый VU через `setup()`, в каждой итерации POST /orders → сразу POST /orders/{id}/cancel → это освобождает HasActiveOrder. НО rate limit всё равно сработает — нужно отключить.
- Альтернатива: сделать POST /orders только в начале теста (ramping scenario), основная нагрузка — GET.
- Заменить `--network host` на `docker compose --profile loadtest run k6` или `docker run --network=arch-hw-1_default ...`.
- Добавить `--summary-export` и `--out json=results.json` для артефактов.

## Пункт 8 — E2E + load + metrics

**Вердикт:** 7/10 — логика верная, но пороги могут не сработать из-за проблем пункта 7

**Риски:**

1. **Error rate при rate-limit.** Если POST /orders возвращает 429/409 — это inflates `http_request_errors_total` (если считать 4xx ошибками). PromQL `sum(rate(http_request_errors_total[1m])) / sum(rate(http_requests_total[1m]))` покажет > 1% → CI упадёт. Решения из пункта 7 обязательны.

2. **`check-sli.sh` timing.** «Ждёт scrape (15s после конца)» — нужно `sleep 15` между окончанием k6 и запросом к Prometheus. Если k6 + sleep + check = ~80s, а в CI есть timeout — нужно учитывать.

3. **PromQL в bash.** `curl 'http://localhost:9090/api/v1/query?query=...'` — query нужно URL-encode. PromQL с `{}[]` содержит спецсимволы. Использовать `--data-urlencode 'query=...'` с POST:
   ```bash
   curl -s --data-urlencode "query=sum(rate(http_request_errors_total[1m])) / sum(rate(http_requests_total[1m]))" \
     http://localhost:9090/api/v1/query
   ```

4. **`jq` парсинг Prometheus response.** Prometheus API v1 возвращает:
   ```json
   {"status":"success","data":{"resultType":"vector","result":[{"metric":{},"value":[1234567890,"0.005"]}]}}
   ```
   Нужно: `.data.result[0].value[1]` — строка! Сравнение в bash: `bc` или `awk`. План не детализирует парсинг.

5. **Порог p95 < 500ms.** В PromQL `histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[1m])) by (le))` возвращает значение в **секундах**. Сравнивать нужно с `0.5`, а не с `500`.

6. **«needs: load-tests»** — значит нужно заново поднять compose? Или переиспользовать? Если отдельный job — compose уже down. Нужно `docker compose up -d --wait` снова. Это добавляет ~30s.

**Рекомендации:**

- В `check-sli.sh` использовать `curl -sG --data-urlencode` для безопасной передачи PromQL.
- Сравнение: `echo "$value > 0.01" | bc -l` возвращает 1 (true) или 0.
- Добавить `set -euo pipefail` в скрипт.
- Пороги: error_rate сравнивать с `0.01` (1%), p95 с `0.5` (500ms = 0.5s).
- Добавить fallback: если `result` пустой (нет данных) — считать это ошибкой (не прошло ни одного scrape).
- Можно объединить `load-tests` и `metrics-check` в один job (k6 → sleep → check-sli.sh) для экономии времени CI.

## Пункт 9 — Alert rules

**Вердикт:** 9/10 — покрывает требования полностью

**Риски:**

1. **`alerts.yml` path.** План: `infra/prometheus/alerts.yml`. Prometheus config должен ссылаться на него: `rule_files: ["/etc/prometheus/alerts.yml"]`. Docker mount: `-v ./infra/prometheus/alerts.yml:/etc/prometheus/alerts.yml`. Нужно убедиться, что prometheus.yml лежит в том же volume, или использовать directory mount.

2. **HighErrorRate PromQL:** `sum(rate(http_request_errors_total[5m])) / sum(rate(http_requests_total[5m])) > 0.05` — **без `for: 5m`** в YAML это будет firing сразу после одного evaluation. План указывает `for 5m` в тексте, но нужно убедиться, что YAML содержит `for: 5m`.

3. **HighLatency:** `histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le)) > 1` — значение 1 = 1 секунда. Задание говорит «p95>1s/5m» — совпадает.

4. **ServiceDown:** `up{job=~"marketplace-api|user-service"} == 0 for 1m` — корректно. Но job names должны совпадать с `job_name` в prometheus.yml scrape config. План: job names = `marketplace-api`, `user-service`. Нужно проверить.

5. **Alertmanager minimal config.** `receivers: [{name: 'null'}]` + `route: {receiver: 'null'}` — алерт видно в AM UI, но не отправляется никуда. ОК для демо.

6. **`demo-alert.sh`: `docker compose stop user-service` → ServiceDown через 1m.** Корректно. Но после stop нужно дождаться 1 min + evaluation_interval (default 1m в Prometheus). Итого ~2 min до firing. Скрипт должен подождать и проверить через AM API.

**Рекомендации:**

- В `prometheus.yml` использовать directory mount:
  ```yaml
  rule_files:
    - "/etc/prometheus/alerts.yml"
  ```
  Docker: `-v ./infra/prometheus:/etc/prometheus`.
- `demo-alert.sh` должен:
  1. `docker compose stop user-service`
  2. `sleep 120`
  3. `curl http://localhost:9093/api/v2/alerts | jq '.[] | select(.labels.alertname=="ServiceDown")'`
  4. Exit 0 если найден alert в state=firing.
- Добавить `evaluation_interval: 15s` в `prometheus.yml` `global:` для ускорения демо.

## Общие риски и упущения

1. **arm64 — БЛОКЕР ВСЕГО CI.** Без исправления Dockerfile/compose ничего не заработает в GitHub Actions. Это приоритет №1.

2. **user-service зависимость от postgres в compose.** В текущем `docker-compose.yml` у `user-service` нет `depends_on`. После рефакторинга (с БД) сервис упадёт при старте, если postgres не готов. Нужно добавить `depends_on: postgres: condition: service_healthy`.

3. **Общий JWT_SECRET.** Если user-service выдаёт JWT, а marketplace-api валидирует через user-service (HTTP call) — secret не нужен в marketplace-api. Но если marketplace-api всё ещё хранит `JWT_SECRET` env var — это лишнее и confusing. Нужно вычистить.

4. **goose миграции — порядок выполнения.** marketplace-api: `00001_init.sql` (создаёт users, products, orders...), `00002_indexes.sql`, `00003_drop_user_tables.sql`. user-service: `00001_init.sql` (создаёт users, refresh_tokens). Если одна БД — порядок зависит от того, кто стартует первым. Если marketplace-api мигрирует первым и дропает users — user-service не сможет создать users (она уже дропнута). Если user-service первый — marketplace-api дропает его таблицы. **Нужна чёткая схема зависимостей миграций или отдельные БД.**

5. **Нет линтера в CI.** План упоминает `go vet` — это минимум. Для реального CI нужен `golangci-lint`. Не критично для оценки, но улучшает качество.

6. **Нет `.dockerignore`.** В `services/marketplace-api/` нет `.dockerignore`. При `COPY . .` в Dockerfile копируются `go.sum`, тесты, `.git` (если есть). Не критично, но увеличивает build context.

7. **Нет docker-compose override для тестов.** E2E и load tests требуют `ORDER_RATE_LIMIT_MINUTES=0`, возможно другие настройки. Нужен `docker-compose.test.yml` или environment override.

8. **Prometheus storage.** В docker-compose не указан volume для Prometheus. При `docker compose down` все метрики теряются. Для CI это нормально, но для локальной разработки — нет. Можно добавить named volume.

9. **Grafana anonymous access.** Для CI/демо Grafana должна быть доступна без логина: `GF_AUTH_ANONYMOUS_ENABLED=true`, `GF_AUTH_ANONYMOUS_ORG_ROLE=Viewer`. Иначе скрипты не смогут обращаться к API.

10. **k6 и ARM.** Образ `grafana/k6` мультиплатформенный — ОК. Но если compose имеет `platform: linux/arm64` — k6 запустится в arm64 в CI = проблема из пункта 1.
